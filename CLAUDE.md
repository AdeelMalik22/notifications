# NotificationOS development context

## Current state

Phase 1 (foundation and operational readiness) plus the initial architecture
and tenancy slice are complete and pushed to `main`. The project is a Django + Django REST Framework modular monolith, not a
microservice system. The Django project package is named `notifications`.

The repository layout is deliberately flat:

```text
.
├── manage.py
├── notifications/       # Django project package
├── apps/                # Django domain apps
├── tests/
├── compose.yaml
└── plan.md
```

Do not add another wrapper directory around the project and do not create a
second nested `notifications/notifications/` package.

## Decisions already made

- Backend: Django 5.2 LTS, DRF, Celery, PostgreSQL, Redis, RabbitMQ.
- Architecture: one deployable codebase with separate web, migration, and
  worker processes; no microservices for the MVP.
- Async work: RabbitMQ is the Celery broker; Celery results are disabled.
  PostgreSQL will be the source of truth for notification and delivery state.
- Redis: cache, locks, and future rate-limit counters only; never the source of
  truth for delivery or idempotency state.
- Local email: Mailpit. Local SMS: deterministic fake adapter. The later real
  SMS provider is Twilio-compatible.
- Liveness (`/health/live`) checks only the web process. Readiness
  (`/health/ready`) checks PostgreSQL and Redis; it intentionally does not make
  API availability depend on RabbitMQ or workers.
- Project logs are JSON and request IDs are validated/generated by middleware.
  Do not log notification body content, recipient contacts, credentials, or
  provider secrets.
- Production settings fail closed for `DJANGO_SECRET_KEY` and
  `DJANGO_ALLOWED_HOSTS`.

## Important commands

```bash
make install        # install exactly from uv.lock
make check          # local formatting/lint/type/test/schema/Compose gates
make ci             # stricter host-side gate, including coverage and deploy checks
make up             # build and start the local stack
make smoke          # probe endpoints, infrastructure, and the Celery worker
make migrate        # run the one-shot migration container
make down           # stop stack while preserving developer volumes
```

For a clean local start:

```bash
cp .env.example .env
make up
make smoke
```

## CI workflow rule

The GitHub Actions workflow in `.github/workflows/ci.yml` is authoritative.
Before reporting a push as successful, run the equivalent local gates and
verify the latest `main` workflow has completed successfully with `gh run
list --workflow ci.yml --branch main`. If a run fails, inspect it with `gh run
view <run-id> --log-failed`, fix the underlying issue, and push a repair before
continuing feature work. Do not infer success from local checks alone.

## Implementation conventions

- Keep business writes in explicit service functions; serializers validate
  transport data and selectors own reads.
- Avoid business-critical Django signals.
- Every tenant-owned table must have a non-null `business_id`; derive tenant
  identity from authentication, never from a request body.
- Use JSON-only Celery payloads with opaque row IDs and trace metadata. Never
  put rendered content, contacts, credentials, or other PII in broker messages.
- New API endpoints go under `/api/v1/`; retain OpenAPI coverage and tests.
- Add migrations with the model change and always run
  `python manage.py makemigrations --check --dry-run` before committing.
- Unit tests use in-memory SQLite and locmem cache. Any behavior relying on
  PostgreSQL, Redis, RabbitMQ, or a worker needs a real integration test.
- Provider secrets must use `PROVIDER_ENCRYPTION_KEY`; never commit `.env`, raw
  credentials, or provider secrets. Local settings load `.env` automatically;
  production and test settings do not.
